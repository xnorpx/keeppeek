The KeepPeek Book

MCP server and LLM configuration

KeepPeek includes built-in Model Context Protocol (MCP) support so AI assistants and MCP clients (such as Claude, Codex, Cursor, and Gemini) can inspect recorder health, logs, events, storage, and recording coverage, and preview or apply validated configuration changes.

MCP is disabled by default for network access. You can connect locally through the keeppeek mcp stdio bridge or enable the embedded Streamable HTTP endpoint (POST /mcp) in config.toml.

flowchart LR
    A[Local AI client] -->|stdio JSON-RPC| B[keeppeek mcp bridge]
    B -->|Bearer auth over HTTP or HTTPS| K[KeepPeek POST /mcp]
    R[Remote MCP client] -->|HTTPS Bearer auth| P[Trusted reverse proxy or VPN]
    P --> K

Use the bundled agent skill

KeepPeek ships a canonical agent skill (skills/keeppeek-mcp/SKILL.md) that teaches LLM assistants how to locate config.toml and secrets.toml, use {secret:KEY} references, run plan_configuration_change before requesting writes, and respect privacy and role boundaries.

Print the skill from any installed KeepPeek binary or export it to a directory:

keeppeek mcp skill
keeppeek mcp skill --output ./skills/keeppeek-mcp

Enable and configure [mcp]

All MCP server settings live in the existing config.toml under [mcp]. Every capability that opens network access, mutates configuration, or captures camera frames defaults to false.

Stop KeepPeek before editing config.toml manually, add [mcp], and restart the server:

enabled = true
allow_writes = false
allow_snapshots = false
max_concurrent_requests = 4
max_response_bytes = 65536
request_timeout_seconds = 15
max_snapshot_bytes = 262144
max_snapshot_dimension = 1280

Connect an MCP client

Create a dedicated named credential in Settings > Access & roles for each MCP client so its activity appears separately in audit records and can be rotated or revoked independently. Use the User role for camera-scoped read-only monitoring, or Administrator for full diagnostics and configuration management. See Authentication and access control.

Local stdio bridge

Most desktop AI assistants launch MCP servers over stdio. KeepPeek provides a built-in stdio JSON-RPC bridge that talks to your KeepPeek server over POST /mcp (with [mcp].enabled = true):

keeppeek mcp [--server <URL>] [--config <PATH>] [--credential-file <PATH>] [--read-only]
  • --server <URL> targets a specific KeepPeek server origin (for example http://127.0.0.1:8081 or https://keeppeek.example.net).
  • --config <PATH> selects an alternate config.toml when resolving local server settings.
  • --credential-file <PATH> reads the Bearer access key from an owner-only file instead of an environment variable.
  • --read-only sends X-KeepPeek-MCP-Read-Only: true, blocking all write tools even if the server has [mcp].allow_writes = true.
  • stdout is reserved strictly for newline-delimited JSON-RPC messages; warnings and logs go to stderr.

Example MCP client configuration (Claude Desktop, Cursor, or other mcpServers clients) using an environment variable:

{
  "mcpServers": {
    "keeppeek": {
      "command": "keeppeek",
      "args": ["mcp", "--server", "http://127.0.0.1:8081", "--read-only"],
      "env": {
        "KEEPPEEK_ACCESS_KEY": "replace-with-dedicated-access-key"
      }
    }
  }
}

Example using an owner-only credential file (chmod 600 on Unix) so the access key is not stored inside the MCP client’s JSON file:

{
  "mcpServers": {
    "keeppeek": {
      "command": "keeppeek",
      "args": [
        "mcp",
        "--server",
        "https://keeppeek.example.net",
        "--credential-file",
        "/path/to/keeppeek-mcp.key",
        "--read-only"
      ]
    }
  }
}

Remove "--read-only" only when you intentionally allow the assistant to apply approved changes against a server configured with [mcp].allow_writes = true.

Remote Streamable HTTP (POST /mcp)

Clients that support MCP Streamable HTTP directly can send JSON-RPC requests to POST /mcp once [mcp].enabled = true is configured and KeepPeek has restarted:

POST /mcp HTTP/1.1
Host: keeppeek.example.net
Authorization: Bearer replace-with-dedicated-access-key
Content-Type: application/json
X-KeepPeek-MCP-Read-Only: true

Example remote MCP client configuration:

{
  "mcpServers": {
    "keeppeek": {
      "url": "https://keeppeek.example.net/mcp",
      "headers": {
        "Authorization": "Bearer replace-with-dedicated-access-key",
        "X-KeepPeek-MCP-Read-Only": "true"
      }
    }
  }
}

Omit X-KeepPeek-MCP-Read-Only when the client needs to call approved write tools and the server enables [mcp].allow_writes = true.

When exposing POST /mcp beyond loopback, keep [access].require_secure_remote = true and terminate HTTPS at a trusted reverse proxy listed in [access].trusted_proxies, or reach KeepPeek over a private VPN. Direct plain HTTP from a remote-classified address is rejected with HTTP 426.

Safe configuration workflow

KeepPeek enforces plan-before-apply so an assistant never modifies cameras or storage blindly:

  1. Inspect the current configuration (get_configuration) and available secret key names (list_secret_keys).
  2. Add any new camera or integration passwords directly to secrets.toml on the server (or via KEEPPEEK_SECRET_<KEY> in the server environment) and reference them as {secret:KEY} or {secret:KEY|url}. Never paste raw passwords into an LLM prompt.
  3. Run discover_cameras (read-only LAN probe) if adding new devices, then call plan_configuration_change (or preview a manage_camera / manage_notification_rule payload).
  4. Review the returned redacted diff, validation errors, revision, and live-apply versus restart summary.
  5. Approve the plan explicitly, then allow the assistant to call apply_configuration_plan (or the approved manage_camera / manage_notification_rule write action).
  6. Check get_server_health and search_logs to confirm activation, or restart KeepPeek when the plan reports that a restart is required.

See Visual configuration management for revision conflicts, inheritance, and template rules.

Security, privacy, and resource boundaries

Authentication, RBAC, and audit

POST /mcp reuses KeepPeek’s standard [access] authentication and authorization pipeline:

  • Remote requests require an active Bearer credential in the Authorization header. Query-string tokens are rejected, and failed authentication rate limits apply.
  • User credentials can call only get_server_health, search_events, get_recording_coverage, and (when enabled) get_camera_snapshot, strictly scoped to their granted cameras.
  • Administrator credentials are required for logs, configuration, secret key listing, discovery, storage, notifications, profiles, and write tools.
  • Privileged reads, configuration mutations, and snapshot requests record bounded entries in KeepPeek’s security audit without logging raw credentials or image bytes.

Remember that KeepPeek’s [access].local_networks policy grants Administrator access to trusted local addresses. Narrow local_networks if a local MCP client must be restricted to a User credential.

Secret redaction

Every MCP response, configuration snapshot, dry-run diff, log search result, and error passes through serialization-layer secret redaction before leaving KeepPeek:

  • Raw values loaded from secrets.toml (including URL percent-encoded variants) are scrubbed.
  • Fields with credential-like names (password, secret, token, access_key, verifier, cookie, authorization, api_key, private_key) are redacted unless they are already {secret:KEY} or {secret:KEY|url} references.
  • Embedded URL credentials (scheme://user:pass@host) are scrubbed while {secret:KEY} and {secret:KEY|url} tokens remain visible for safe editing.

DNS rebinding and cross-origin protection

POST /mcp validates the Host header and enforces an explicit browser origin allowlist:

  • Non-browser MCP clients that omit Origin are permitted.
  • Unauthenticated local requests (when [access].local_networks grants local trust) require Host to be localhost or an IP literal (127.0.0.1, [::1]) so DNS-rebound domain names are rejected with 403.
  • Requests carrying a browser Origin header are rejected with 403 unless the exact origin is listed in [direct_card].allowed_origins, and require Authorization: Bearer <key> even on local networks (returning 401 if unauthenticated).
  • Unsupported HTTP methods on /mcp return 405 Method Not Allowed, and a disabled MCP server returns 404 Not Found.

Fail-closed privacy and snapshot limits

get_camera_snapshot enforces four sequential gates before returning any image bytes:

  1. [mcp].allow_snapshots must be true.
  2. The authenticated principal must have view permission for the requested camera.
  3. The per-camera rate limit (snapshot_min_interval_seconds) must not be exceeded.
  4. Camera privacy state ([privacy] schedules and runtime profile overrides) must be verified as inactive. If privacy mode is active or cannot be verified, KeepPeek fails closed and refuses the snapshot.

Decoded frames use bounded image decoder limits, downscale to at most max_snapshot_dimension pixels per side while preserving aspect ratio, and encode JPEG within max_snapshot_bytes. KeepPeek does not apply server-side pixel masks; only camera-side (hardware) privacy masks already rendered into the camera stream appear in the returned frame.

Concurrency and payload caps

KeepPeek caps simultaneous MCP executions at max_concurrent_requests, enforces request_timeout_seconds, and rejects oversized JSON-RPC responses above max_response_bytes (get_camera_snapshot uses max_snapshot_bytes plus base64 and metadata envelope overhead) so an automated assistant cannot starve camera ingest, recording, or live playback.

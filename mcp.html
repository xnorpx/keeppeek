The KeepPeek Book

MCP server and LLM configuration

KeepPeek includes built-in Model Context Protocol (MCP) support so AI assistants and MCP clients (such as Claude, Codex, Cursor, and Gemini) can inspect recorder health, logs, events, storage, and recording coverage, onboard and tune cameras without exposing plaintext credentials, and preview or apply validated configuration changes.

MCP is disabled by default for network access. You can connect locally through the keeppeek mcp stdio bridge or enable the embedded Streamable HTTP endpoint (POST /mcp) in config.toml.

flowchart LR
    A[Local AI client] -->|stdio JSON-RPC| B[keeppeek mcp bridge]
    B -->|Bearer auth over HTTP or HTTPS| K[KeepPeek POST /mcp]
    R[Remote MCP client] -->|HTTPS Bearer auth| P[Trusted reverse proxy or VPN]
    P --> K
    U[Local operator browser] -->|Loopback single-use token| S[GET/POST /mcp/secret-entry]
    S --> K

Enable and configure [mcp]

All MCP server settings live in the existing config.toml under [mcp]. Every capability that opens network access, mutates configuration, writes on-camera hardware settings, captures camera frames, or captures raw camera traffic defaults to false.

A human Administrator can enable or disable MCP access live without restarting KeepPeek from Settings > Integrations > MCP server (trusted local network access or an interactive OIDC/identity-proxy browser session; explicit confirmation is required to enable — remote browser sessions authenticated with a Bearer access key cannot enable MCP or silence warnings). To change policy limits (allow_writes, allow_snapshots, allow_camera_device_writes, or payload/rate caps), stop KeepPeek before editing config.toml manually, add [mcp], and restart the server:

[mcp]
enabled = true
allow_writes = false
allow_snapshots = false
allow_camera_device_writes = false
allow_camera_debugging = false
debug_camera_ids = []
max_debug_capture_bytes = 67108864
max_debug_storage_bytes = 536870912
max_concurrent_requests = 4
max_response_bytes = 65536
request_timeout_seconds = 15
max_snapshot_bytes = 262144
max_snapshot_dimension = 1280
snapshot_min_interval_seconds = 5

Security warning: Setting [mcp].allow_camera_debugging = true grants Administrator MCP clients and AI assistants full raw access to live video bitstreams, audio streams, decrypted network captures (PCAPNG), and camera credentials for debug_camera_ids (or all configured cameras when empty). KeepPeek emits a prominent tracing::warn! on startup and adds a warning issue to ServerHealthResponse whenever both enabled and allow_camera_debugging are true. Enable it only during active protocol debugging and set allow_camera_debugging = false afterward.

Human-only enable, agent self-disable, and 7-day warning

MCP access is designed as a temporary maintenance surface rather than an unmonitored permanent open door:

  • Agent self-disable (disable_mcp_access): An authenticated Administrator agent can turn off MCP access itself when finished by calling disable_mcp_access with { "confirm": true } (and an optional reason). This works even when [mcp].allow_writes = false (though it is blocked under --read-only / X-KeepPeek-MCP-Read-Only: true), persists [mcp].enabled = false in config.toml (and fails safe by still turning MCP off live if config.toml persistence fails), drops any pending /mcp/secret-entry handoffs, and immediately switches new /mcp and /mcp/secret-entry requests to 404 without a restart (already in-flight /mcp calls finish within request_timeout_seconds).
  • Human-only enable and warning silence: No MCP tool can enable MCP or silence the 7-day warning. Enabling MCP or silencing the warning over the WebRTC control plane (keeppeek.mcp-access.v1) requires a human Administrator (trusted local network or interactive OIDC/identity-proxy browser session) and rejects Bearer access-key credentials with 403 (including remote browser sessions signed in with an access key). Bearer-authenticated configuration restores (POST /config/apply) are also rejected with 403 if they attempt to enable [mcp], silence the warning, advance or omit enabled_at_unix_secs, escalate [mcp] write/snapshot flags, or alter [access], [external_auth], or [external_identities] trust policy.
  • 7-day enabled warning: When [mcp].enabled stays true for 7 days or longer (>= 604,800 seconds) without being silenced, KeepPeek logs a startup warning, adds an Administrator-only warning to server health (scope: "mcp"), and displays an Administrator warning banner in the Web UI with direct Disable MCP and Silence warning actions. Silencing persists long_enabled_warning_silenced = true for the current enabled stretch; disabling MCP and later re-enabling it resets the timer and clears the silence flag.

See Configuration reference for validation rules and file ownership details.

Connect an MCP client

Create a dedicated named credential in Settings > Access & roles for each MCP client so its activity appears separately in audit records and can be rotated or revoked independently. Use the User role for camera-scoped read-only monitoring, or Administrator for full diagnostics, camera onboarding, hardware tuning, and configuration management. See Authentication and access control.

Local stdio bridge

Most desktop AI assistants launch MCP servers over stdio. KeepPeek provides a built-in stdio JSON-RPC bridge that talks to your KeepPeek server over POST /mcp (with [mcp].enabled = true):

keeppeek mcp [--server <URL>] [--config <PATH>] [--credential-file <PATH>] [--read-only]
  • --server <URL> targets a specific KeepPeek server origin (for example http://127.0.0.1:8081 or https://keeppeek.example.net).
  • --config <PATH> selects an alternate config.toml when resolving local server settings.
  • --credential-file <PATH> reads the Bearer access key from an owner-only file instead of an environment variable.
  • --read-only sends X-KeepPeek-MCP-Read-Only: true, blocking all configuration and on-camera hardware write tools even if the server enables [mcp].allow_writes or [mcp].allow_camera_device_writes.
  • stdout is reserved strictly for newline-delimited JSON-RPC messages; warnings and logs go to stderr.

Example MCP client configuration (Claude Desktop, Cursor, or other mcpServers clients) using an environment variable:

{
  "mcpServers": {
    "keeppeek": {
      "command": "keeppeek",
      "args": ["mcp", "--server", "http://127.0.0.1:8081", "--read-only"],
      "env": {
        "KEEPPEEK_ACCESS_KEY": "replace-with-dedicated-access-key"
      }
    }
  }
}

Example using an owner-only credential file (chmod 600 on Unix) so the access key is not stored inside the MCP client’s JSON file:

{
  "mcpServers": {
    "keeppeek": {
      "command": "keeppeek",
      "args": [
        "mcp",
        "--server",
        "https://keeppeek.example.net",
        "--credential-file",
        "/path/to/keeppeek-mcp.key",
        "--read-only"
      ]
    }
  }
}

Remove "--read-only" only when you intentionally allow the assistant to apply approved changes against a server configured with [mcp].allow_writes = true or [mcp].allow_camera_device_writes = true.

Remote Streamable HTTP (POST /mcp)

Clients that support MCP Streamable HTTP directly can send JSON-RPC requests to POST /mcp once [mcp].enabled = true is configured and KeepPeek has restarted:

POST /mcp HTTP/1.1
Host: keeppeek.example.net
Authorization: Bearer replace-with-dedicated-access-key
Content-Type: application/json
X-KeepPeek-MCP-Read-Only: true

Example remote MCP client configuration:

{
  "mcpServers": {
    "keeppeek": {
      "url": "https://keeppeek.example.net/mcp",
      "headers": {
        "Authorization": "Bearer replace-with-dedicated-access-key",
        "X-KeepPeek-MCP-Read-Only": "true"
      }
    }
  }
}

Omit X-KeepPeek-MCP-Read-Only when the client needs to call approved write tools and the server enables [mcp].allow_writes = true or [mcp].allow_camera_device_writes = true.

When exposing POST /mcp beyond loopback, keep [access].require_secure_remote = true and terminate HTTPS at a trusted reverse proxy listed in [access].trusted_proxies, or reach KeepPeek over a private VPN. Direct plain HTTP from a remote-classified address is rejected with HTTP 426.

Fast local development and agentic MCP loop

Because POST /mcp is stateless, AI agents testing local KeepPeek changes can stay connected across live supervised binary swaps without restarting the agent or editing MCP client config:

  1. Start the supervisor once with local channel opt-in and a short probation window:

    keeppeek-supervisor run --root <dev-supervisor-root> --config <path/to/config.toml> --allow-local --probation-ms 500

  2. Point the MCP client directly at Streamable HTTP (http://127.0.0.1:8081/mcp). On Windows, prefer Streamable HTTP (or a copied keeppeek.exe outside target/) over running target/debug/keeppeek.exe mcp directly so Cargo can relink target/debug/keeppeek.exe without a file lock.

  3. After editing Rust code, rebuild and hot-swap the running child in one command:

    cargo build --bin keeppeek
keeppeek-supervisor update --root <dev-supervisor-root> --channel local --binary target/debug/keeppeek --apply --wait --json

  4. Confirm the new child PID/executable via get_server_health (system.process.pid and system.process.executable) or keeppeek-supervisor status --root <dev-supervisor-root> --json. If the new binary crashes or fails probation, the supervisor automatically rolls back to the previous working slot and reports rolled_back: true.

Manage secrets without plaintext chat (keeppeek secret and loopback UI handoff)

KeepPeek never accepts raw camera passwords or webhook secrets through MCP tool arguments, and assistants should never ask you to paste passwords into chat. Store secrets in secrets.toml out-of-band using either the local CLI or the loopback secret-entry handoff, then reference them as {secret:KEY} or {secret:KEY|url}.

keeppeek secret CLI

Manage secrets.toml entries directly from a local shell without ever placing secret values in command-line arguments:

keeppeek secret set <KEY> [--config <PATH>] [--server <URL>] [--stdin]
keeppeek secret list [--config <PATH>]
keeppeek secret remove <KEY> [--config <PATH>]
  • Keys must match ^[A-Z_][A-Z0-9_]*$ (1–128 bytes); values must be non-empty, at most 4 KiB, and contain no NUL bytes.
  • keeppeek secret set reads values only from a no-echo interactive terminal prompt or --stdin (never from positional arguments or flags).
  • keeppeek secret list prints sorted key names only and never prints values.
  • Writes use owner-only file permissions (0600 on Unix / owner-only DACL on Windows), atomic replacement under the shared configuration lock, and zeroized temporary buffers.
  • A running KeepPeek server automatically detects secrets.toml updates so newly added keys work immediately in probe_camera_streams and manage_camera without restarting.

Loopback-only secret-entry UI handoff (GET / POST /mcp/secret-entry)

When an assistant discovers that a secret key is missing from list_secret_keys, it can call request_secret_entry to create a short-lived, single-use handoff (60..=300 seconds, default 180, capped at 16 pending handoffs). KeepPeek returns a loopback URL:

http://127.0.0.1:<port>/mcp/secret-entry?token=<256-bit-single-use-token>
  • Open the link locally on the recorder host, enter the values in the self-contained HTML form, and submit. KeepPeek writes secrets.toml atomically, reloads secrets live without a restart, invalidates the token immediately, emits a value-free audit event, and never echoes secret values.
  • The assistant polls get_secret_entry_status, which returns only status ("pending", "completed", "expired", or "failed"), configured_keys, and expires_at_ms.
  • /mcp/secret-entry is strictly loopback-only: non-loopback connections, proxy-forwarded requests, non-loopback Host headers, and cross-origin POST requests are rejected with 403. When [mcp].enabled = false, /mcp/secret-entry returns 404.
  • Form responses enforce Cache-Control: no-store, Referrer-Policy: same-origin, X-Frame-Options: DENY, and a strict Content Security Policy.

Multi-candidate stream probing and on-camera hardware support

Pre-populated secrets.toml multi-candidate probing

If a site uses a few known camera credential pairs already stored in secrets.toml, an assistant can pass up to 5 {secret:KEY} pairs in probe_camera_streams.credential_candidates:

  • Raw credential fields and inline RTSP userinfo or query-string credentials are rejected.
  • Targets are SSRF-bounded: unspecified, multicast, broadcast, link-local (169.254.0.0/16), public IPs, unconfigured loopback addresses, and mismatched RTSP URL hosts are blocked.
  • Probing stops immediately on the first matching credential pair or if the camera reports lockout, HTTP 429, or becomes unreachable.
  • Responses return only matched_credentials ({secret:KEY} references), failed_candidates indexes, recommended_backend, verified RTSP URLs, and redacted diagnostics.

Deep camera protocol debugging and offline replay

When standard health and log tools are not enough to diagnose an RTSP, RTP, ONVIF, ISAPI, or Reolink Baichuan (reo_proto) interoperability defect, enable [mcp].allow_camera_debugging = true temporarily and export the keeppeek-camera-debug skill (keeppeek mcp skill camera-debug).

  1. Capture on the running server: Run camera_debugging (inspect_pipeline -> capture -> compare_transports). KeepPeek writes bounded artifacts under <config-dir>/camera-debug/<capture-id>/ (capture.pcapng with Ethernet/IP/TCP/UDP framing around decrypted payloads, raw .h264/.h265 and audio elementary streams, rtp_packets.bin when raw RTP dump is enabled, muxed.mp4, sdp.txt, protocol_transcript.json, and atomically written capture.json) with a 24-hour TTL and FIFO eviction at max_debug_storage_bytes.
  2. Triage locally with standard tools: Inspect capture.pcapng with tshark (-Y "rtsp || rtp || http || xml", -z follow,tcp,ascii,0, -T fields -e rtp.seq -e rtp.timestamp -e h264.nal_unit_type), ffprobe -show_packets -show_frames muxed.mp4, and ffmpeg -v error -i video.h264 -f null -.
  3. Export a sanitized fixture and reproduce offline: Call camera_debugging (action: "export_repro_fixture", strip_credentials: true, anonymize_network: true) and verify sharing_safety_report.safe_to_share_publicly is true (RFC 5737 192.0.2.x addresses and stripped credentials). Reproduce deterministically using ReplayCameraServer in crates/test-camera/src/replay.rs (keeppeek.camera-repro.v1) or interactively via keeppeek-camera replay --fixture <PATH> [--bind 127.0.0.1:0] [--once | --loop]. Build and test fixes locally with cargo nextest and cargo run --bin keeppeek against a test configuration (live binary hot-swap via keeppeek-supervisor is coming separately).
  4. Clean up and re-lock: Delete local captures with camera_debugging (action: "delete_capture"), stop KeepPeek, set allow_camera_debugging = false in config.toml, and restart KeepPeek.

Safe configuration workflow

KeepPeek enforces plan-before-apply so an assistant never modifies cameras, hardware settings, or storage blindly:

  1. Inspect the current configuration (get_configuration) and available secret key names (list_secret_keys).
  2. Add missing camera or integration passwords out-of-band via keeppeek secret set <KEY> or the loopback request_secret_entry UI handoff (or KEEPPEEK_SECRET_<KEY> in the server environment), and reference them as {secret:KEY} or {secret:KEY|url}. Never paste raw passwords into an LLM prompt.
  3. Run discover_cameras and search_camera_catalog for new devices, verify streams with probe_camera_streams, then call plan_configuration_change (or preview a manage_camera / manage_notification_rule payload).
  4. Review the returned redacted diff, validation errors, revision, and live-apply versus restart summary.
  5. Approve the plan explicitly, then allow the assistant to call apply_configuration_plan (or the approved manage_camera / manage_notification_rule write action).
  6. If tuning on-camera settings, inspect with get_camera_device_settings, preview with update_camera_device_settings (dry_run: true), approve explicitly, and apply with dry_run: false (requires [mcp].allow_camera_device_writes = true).
  7. Check get_server_health and search_logs to confirm activation, or restart KeepPeek when the plan reports that a restart is required.

See Visual configuration management for revision conflicts, inheritance, and template rules.

Security, privacy, and resource boundaries

Authentication, RBAC, and audit

POST /mcp reuses KeepPeek’s standard [access] authentication and authorization pipeline:

  • Remote requests require an active Bearer credential in the Authorization header. Query-string tokens are rejected, and failed authentication rate limits apply.
  • User credentials can call only get_server_health, search_events, get_recording_coverage, and (when enabled) get_camera_snapshot, strictly scoped to their granted cameras.
  • Administrator credentials are required for logs, configuration, secret key listing, secret entry handoffs, catalog search, stream probing, discovery, storage, notifications, profiles, hardware settings, and write tools.
  • Privileged reads, configuration mutations, secret-entry submissions (key names only), on-camera hardware updates, and snapshot requests record bounded entries in KeepPeek’s security audit without logging raw credentials or image bytes.

Remember that KeepPeek’s [access].local_networks policy grants Administrator access to trusted local addresses. Narrow local_networks if a local MCP client must be restricted to a User credential.

Secret redaction

Every MCP response, configuration snapshot, dry-run diff, probe diagnostic, log search result, and error passes through serialization-layer secret redaction before leaving KeepPeek:

  • Raw values loaded from secrets.toml (including URL percent-encoded variants) are scrubbed.
  • Fields with credential-like names (password, secret, token, access_key, verifier, cookie, authorization, api_key, private_key) are redacted unless they are already {secret:KEY} or {secret:KEY|url} references.
  • Embedded URL credentials (scheme://user:pass@host) are scrubbed while {secret:KEY} and {secret:KEY|url} tokens remain visible for safe editing.
  • Explicit camera_debugging boundary: When [mcp].allow_camera_debugging = true, SecretRedactor is bypassed by default on capture and compare_transports (both default include_raw_auth: true — pass include_raw_auth: false to redact), bypassed on inspect_pipeline only when include_raw_auth: true is passed (defaults to false), and bypassed on export_repro_fixture only when strip_credentials: false is passed (defaults to true). SecretRedactor remains strictly enforced on all other 28 MCP tools, error messages, and whenever export_repro_fixture runs with strip_credentials: true.

DNS rebinding and cross-origin protection

POST /mcp validates the Host header and enforces an explicit browser origin allowlist:

  • Non-browser MCP clients that omit Origin are permitted.
  • Unauthenticated local requests (when [access].local_networks grants local trust) require Host to be localhost or an IP literal (127.0.0.1, [::1]) so DNS-rebound domain names are rejected with 403.
  • Requests carrying a browser Origin header are rejected with 403 unless the exact origin is listed in [direct_card].allowed_origins, and require Authorization: Bearer <key> even on local networks (returning 401 if unauthenticated).
  • /mcp/secret-entry is stricter still: it allows loopback peers only, rejects proxy-forwarded headers, and requires an exact same-origin loopback Origin on POST.
  • Unsupported HTTP methods on /mcp or /mcp/secret-entry return 405 Method Not Allowed, and a disabled MCP server returns 404 Not Found.

Fail-closed privacy and snapshot limits

get_camera_snapshot enforces four sequential gates before returning any image bytes:

  1. [mcp].allow_snapshots must be true.
  2. The authenticated principal must have view permission for the requested camera.
  3. The per-camera rate limit (snapshot_min_interval_seconds) must not be exceeded.
  4. Camera privacy state ([privacy] schedules and runtime profile overrides) must be verified as inactive. If privacy mode is active or cannot be verified, KeepPeek fails closed and refuses the snapshot.

Decoded frames use bounded image decoder limits, downscale to at most max_snapshot_dimension pixels per side while preserving aspect ratio, and encode JPEG within max_snapshot_bytes. KeepPeek does not apply server-side pixel masks; only camera-side (hardware) privacy masks already rendered into the camera stream appear in the returned frame.

Concurrency and payload caps

KeepPeek caps simultaneous MCP executions at max_concurrent_requests, enforces request_timeout_seconds, and rejects oversized JSON-RPC responses above max_response_bytes (get_camera_snapshot uses max_snapshot_bytes plus base64 and metadata envelope overhead) so an automated assistant cannot starve camera ingest, recording, or live playback.
